# How pi's TUI displays tool calls and tool output

Source: installed `@earendil-works/pi-coding-agent` **0.87.1**, its bundled `pi-agent-core` and `pi-ai`. The line-number references below describe the installed `dist/` JavaScript at that version; the corresponding tagged first-party TypeScript lives in [pi coding-agent](https://github.com/earendil-works/pi/tree/v0.87.1/packages/coding-agent/src), [pi agent](https://github.com/earendil-works/pi/tree/v0.87.1/packages/agent/src), and [pi AI](https://github.com/earendil-works/pi/tree/v0.87.1/packages/ai/src). This describes that version, not a contract for all versions.

## Before execution: a call appears while the model writes arguments

The model provider emits `toolcall_start`, `toolcall_delta`, `toolcall_end`. For example, the Anthropic adapter creates a tool-call block with name and id on `content_block_start`, appends `input_json_delta` fragments to `partialJson`, parses the accumulated prefix into `arguments`, and removes `partialJson` at block end (`node_modules/@earendil-works/pi-ai/dist/api/anthropic-messages.js:475-480, 507-559`). Agent-core forwards all three as `message_update` with the **current partial assistant message** (`node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js:277-308`). The TUI scans that message: on the first tool-call block it creates a `ToolExecutionComponent` keyed by `content.id`; subsequent updates call `updateArgs(content.arguments)`. It does not wait for `tool_execution_start`. At `message_end`, it marks arguments complete; `tool_execution_start` marks the same component executing, creating it only if it did not already exist (`dist/modes/interactive/interactive-mode.js:2742-2766, 2796-2826`).

**Correction to my earlier recommendation:** pi generally presents a *best-effort parsed argument object*, not necessarily verbatim raw JSON fragments. Its call renderer receives the current arguments, and a generic fallback pretty-prints them; incomplete values can therefore change as parsing progresses (`dist/modes/interactive/components/tool-execution.js:100-104, 223-277, 324-334`). The renderer context distinguishes `argsComplete`, `executionStarted`, and `isPartial` (`dist/modes/interactive/components/tool-execution.js:61-79`). Neither seeing the name nor seeing a rendered field requires waiting for JSON completion.

## During execution: partial *results*, not persisted result messages

A tool may call its `onUpdate(partialResult)` callback. Agent-core emits `tool_execution_update` with `partialResult` and, on completion, `tool_execution_end` with the authoritative result and error status (`node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js:539-566`; `dist/modes/interactive/interactive-mode.js:2828-2844`). The TUI updates the **same keyed component** in place, passing `isPartial: true` to the renderer until the final result. A tool's result is structured `content` (text or image) plus optional `details`; the renderer can display either (`dist/modes/interactive/components/tool-execution.js:106-119, 247-276, 291-315`). An empty partial update can display an executing state without output.

**Streaming is tool-dependent.** Built-in `bash` accumulates process output and sends **whole snapshots**, throttled to at most one per 100 ms; it explicitly flushes a dirty tail at completion (`dist/core/tools/bash.js:158-213, 220-244`; `dist/core/tools/renderers/bash.js:15`). Built-in `read` and `grep` accept but do not call `_onUpdate`: their contents arrive as final results, not live partial output (`dist/core/tools/read.js:42-43, 137-155`; `dist/core/tools/grep.js:37-38, 150-250`). Thus what feels complete for read/search is **final-result availability and rendering**, not token-by-token streaming of file contents or search hits.

## Output visibility has limits

The TUI renders a tool using per-tool `renderCall`/`renderResult`, falling back to generic text when no registered renderer is present (`dist/modes/interactive/components/tool-execution.js:223-285`). `read` deliberately hides successful output unless expanded, then shows the result (10-line compact fallback in its result renderer); `grep` defaults to 15 lines; `bash` defaults to the last five *visual* lines. Expansion shows all of the **returned** result, not data beyond tool-level truncation (`dist/core/tools/renderers/read.js:89-116`; `dist/core/tools/renderers/grep.js:30-52`; `dist/core/tools/renderers/bash.js:42-77`). Generic unregistered tools use a 10-line preview and an expanded full returned result (`dist/modes/interactive/components/tool-execution.js:85-104`). Built-in tools bound model-facing results: common limits are 2,000 lines and 50 KB; truncated bash saves a full-output temp file and advertises its path; read supplies a continuation offset (`dist/core/tools/truncate.js:1-12`; `dist/core/tools/bash.js:221-250`; `dist/core/tools/read.js:112-142`). So “perfectly” does not mean *untruncated* or *always visible by default*.

## Persistence, errors, and what transfers to bb

Pi persists finalized assistant and tool-result messages on `message_end`, not each `message_update` or `tool_execution_update` (`dist/core/agent-session.js:583-599`). On session render, the TUI recreates tool components from assistant tool-call blocks, then matches persisted `toolResult` messages by `toolCallId` (`dist/modes/interactive/interactive-mode.js:3136-3186`). On assistant abort/error it marks still-pending tool components with an error result (`dist/modes/interactive/interactive-mode.js:2775-2799`); tool execution exceptions become error results (`node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js:539-578`).

The portable pattern is **one stable tool-call id, early named provisional call, replaceable partial argument snapshots, replaceable partial result snapshots, authoritative final result, and separate persistence at completion**. Pi achieves fast repaint because the model events, running tools, component state, and terminal renderer live in one process; bb needs explicit bridge/daemon/server/browser representations and transport for each part. This was evidence for [Decide how the delta protocol should represent a tool call still being written](https://github.com/IlyaM/bb/issues/13); that later resolution chose best-effort structured snapshots, with raw fragments deferred. It does **not** say bb must copy pi's preview defaults.
