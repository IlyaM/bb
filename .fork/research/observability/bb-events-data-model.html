What is an “event” in bb?

A thread is a conversation with an agent, but the screen is not a recording of every byte the provider sends. bb receives activity, turns it into durable facts, then builds a readable timeline from those facts. This report separates those layers so we can make the filter decision without confusing them.

The short answer. An event is a recorded occurrence or update in a thread, such as “tool started,” “more output arrived,” or “turn ended.” A row is a screen-oriented interpretation of one or more events, such as a single command card whose output grows. There is no one-event-to-one-row rule.

Start here · The actual stored data model

You’re right to ask for the schema rather than just the journey through the system. bb has one thread event union: each event has an exact type with its own required fields. It is stored as a row in the events SQLite table. An event can describe a provider activity, a user request, or a bb system action. The word “event” below always means this normalized ThreadEvent, unless qualified as a provider-native signal or a bridge delta.

The decoded form used by application code puts threadId, type, and scope back beside the payload. A ThreadEventRow adds the stored ID, sequence (seq), and timestamp (createdAt). Those are three views of the same record, not three separate events. A turn scope is {"kind":"turn","turnId":"turn-1"}; a thread scope is {"kind":"thread"}. Type-to-scope rules reject mismatches. For example, ordinary item start/completion must be turn-scoped, but background task progress is thread-scoped because it can arrive after the turn ends.

1 · The nouns, in plain language

CONTAINER

Thread

One agent conversation/work unit. It owns a history of events, and may own a delegated child thread.

EPISODE

Turn

One stretch of work after a request. It starts, produces messages and work, then completes, fails, or is interrupted. A thread has multiple turns.

HISTORY

Stored event

A sequenced record attached to the thread. It has a type, data, time, and often a turn/item/parent identity. Many records can update the same activity.

IDENTITY

Item / call

The thing evolving over time: an assistant message, command, tool invocation, plan, delegation, etc. Its stable identity lets start, progress, and finish be combined.

READ MODEL

Timeline row

A server-built piece of display data: conversation, work, system, or a turn wrapper. A work row can hold status, argument details, output and nested child rows.

NOT A HISTORY RECORD

Live notification

A WebSocket “thread changed” nudge. It tells the browser to fetch again; it does not carry the event content.

2 · Where the information travels

Read downward. Each boundary serves a different purpose and can lose or reshape detail.

Agent/provider

Pi, Claude Code, Codex, ACP, or a plugin produces provider-specific activity. Some native signals are deliberately classed as noise; different providers expose different detail.

↓
Normalized delta

The provider adapter speaks bb’s bridge vocabulary: turn.open, item.open, item.textDelta, item.outputDelta, item.close, and others. A delta is an input instruction to the assembler, not a timeline row.

↓
Thread event

The assembler turns deltas into events such as item/started, item/commandExecution/outputDelta, item/completed, or turn/completed. bb itself also creates client/system events, for example a user request, provisioning, or an interaction lifecycle.

↓
Stored history

The daemon posts event batches to the server. The server validates and appends events in SQLite, giving each one a per-thread sequence. This history is used for replay, lifecycle state, searches and read models; it is not just UI data.

↓
Server projection

On timeline requests, bb selects an event window and folds related events into messages/work/system rows and current-state summaries (e.g. todos, usage). It may group or omit rows. Older pages and nested children have their own retrieval paths.

↓
Browser view

An HTTP response carries timeline rows, not the raw event ledger. WebSocket changes cause another fetch. The client further arranges rows into activity bundles and renders cards. The CLI can also format timeline rows as text.

Illustrative times and values below—not a literal dump of one provider. The shape is what matters.

00:00

00:01

00:02
item/started — file-read item r1 for config.json begins.
00:03
item/completed — the same item r1 finishes. A different tool such as a shell command may also produce repeated outputDelta events between start and finish.
00:04

A viewer might see only these three content rows from those many events:

You · What does config.json do?
Read file · config.json · completed
Assistant · It configures…

A delta of a sentence is not a new message. A completion event is not necessarily a separate completed card; it usually updates the existing item/row. A turn boundary can instead become a wrapper around rows if collapse mode is enabled.

Important limitation today: the file-read/search row schema has path/query and status but no result-output field. Receiving a start/finish event does not mean the screen can show what was read. Likewise a tool whose adapter discarded its native signal has nothing for a later client-side filter to reveal.

5 · How is an event different from a row?

Event = “what happened?”

  • Stored in order with a sequence in a thread.
  • Can be a small update, a lifecycle transition, an error, or a state snapshot.
  • Many events can belong to one item; not all are intended as distinct visible activities.
  • Some are for control/state, not transcript text.

Row = “how do we present it?”

  • Produced from selected events for an HTTP timeline page.
  • Has a stable row ID, kind, content, status, and possibly parent/child structure.
  • May be a derived turn summary rather than one event.
  • Can be regrouped, hidden, truncated, or paged independently of the stored event history.

Currently the server contract has conversation, work, system, and turn rows. Work has more specific kinds: command, tool, file-change, file-read, search, plan-steps, extension, delegation, workflow, and others. These are row categories, not provider-native event types. A plugin tool can appear as a generic tool row with its own name and presentation metadata. The browser’s buildTimelineViewRows can additionally make inferred activity bundles; that is another presentation layer, not another recorded occurrence.

A necessary correction to the earlier report: “pi plan updates” was an incorrect example of presentation.suppress. The shared planStepsPresentation is used by ACP and Claude Code, not the Pi adapter. Pi’s ordinary tool adapter does not set it. Also, Pi read/grep/find are generic tools; the fileRead/search resultless row gap describes other provider paths, while the generic Pi tool result may arrive only at completion.

Does pi hide nothing? No. It avoids the specific presentation.suppress skip for normal Pi tools, but still loses partial call arguments, can delay text without a newline, can preview/cap output and bundle rows, and defaults to collapsed completed turns without your current flat override. Some raw signals are intentionally ignored as protocol noise (e.g. boundaries already represented elsewhere), so “every raw event gets a row” is not a useful invariant.

7 · A smaller decision may be enough

Nothing in the evidence requires a filtering UI. A user-configurable category system, persistence rules and toolbar would be a separate product feature, not the minimum fix for hiding.

Smallest code-level route

Audit each actual suppression site. Stop dropping distinct work rows in the projection; preserve true duplicate/state information without fabricating another activity row. Keep existing diagnostics as an explicit separate concern. Test each provider and plugin case. This can be code-only, with no filter UI or per-user setting.

Pi-only route

If the goal truly narrows to Pi, the provider-specific presentation.suppress list is largely beside the point. Pi’s important losses are the tool-argument stream, buffering, grouping, previews and any plugin-generated side channels. But this would revise the map’s bb-wide, every-provider charter rather than quietly satisfying it.

Unsettled boundary: Is this effort still specifying bb-wide observability, as the map says, or a Pi-first experience with other providers deferred? That answer determines whether suppressing Claude/ACP/Codex/plugin activities must be removed now. Either route can avoid building a filter UI.

Scope and honesty. This documents the repository’s current path and the already-recorded map decisions; examples are illustrative, not claims about identical behavior across providers. “All available events” does not mean every raw provider signal is captured today. The report informed the now-closed filter decision; no product code was changed.
