# Tool lifecycle: pi, Claude Code, Codex, ACP, and bb

**Research note for [Decide how the delta protocol should represent a tool call still being written](https://github.com/IlyaM/bb/issues/13).** This is an explanation and comparison, **not a resolution** or proposed schema. Based on bb commit `7e8ec7e76`, locally installed pi-coding-agent **0.87.1**, official Claude Agent SDK and ACP documentation, and current OpenAI Codex source inspected during this research. Codex `main` is a moving target; the linked files are the inspected sources, not a claim about every installed version. The tagged pi links point at TypeScript source, while the detailed line references in the earlier research note refer to the installed JavaScript build; their line numbers are not interchangeable. Claude Code's *native CLI renderer internals* are not open source here: its public SDK contract and first-party Desktop view-mode documentation are distinguishable from undocumented CLI rendering internals.

## 1. The conceptual model, before any product names

A tool call crosses **six different boundaries**, which should not be collapsed into one “tool output” field:

```text
model emits tool name/id → model writes input/arguments → input is complete
  → optional permission gate → tool starts → zero or more progress/output updates
  → final result or failure/cancellation → conversation/session stores final record
  → UI presents that record (possibly with its own preview/expansion policy)
```

- **Call**: identity, name, optional provider-specific classification, input under construction. The model is still *asking* to run a tool; no execution output exists yet.
- **Execution**: permission, start, status/progress, possibly streamed output; some tools return only once they finish.
- **Result**: final structured content (text, images, resources, errors) plus metadata. A displayed preview need not be the whole model-facing result; neither need be the whole underlying file or process output.
- **Persistence**: durable transcript of what happened versus provisional screen state. A stream of 1,000 small updates need not become 1,000 permanent rows.
- **Presentation**: label, layout, visibility, expansion, syntax formatting. Hiding a result *in the UI* differs from not receiving or retaining it in the first place.

The same user-visible symptom, “I can't see the output,” can therefore mean the provider never emitted it, the bridge discarded it, the shared schema could not represent it, the projection dropped it, the delivery path delayed it, or the UI collapsed it. A design that fixes only one tool name or one renderer cannot address the other layers.

## 2. pi: a single ID and a mutable local component

**Model → tool call.** In pi's Anthropic adapter, `content_block_start` supplies a `tool_use` name and ID. `input_json_delta` appends raw JSON fragments; the adapter parses the accumulated prefix into the currently available `arguments` object. `toolcall_end` finalizes that object and removes its parsing scratch buffer ([pi-ai Anthropic adapter](https://github.com/earendil-works/pi/blob/v0.87.1/packages/ai/src/api/anthropic-messages.ts)). Agent-core emits `message_update` for **start, delta, and end**, carrying the *current partial assistant message* ([agent-loop.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/agent/src/agent-loop.ts)).

**Tool call → TUI.** On `message_update`, pi's TUI walks the assistant message's tool-call blocks. The first block creates a `ToolExecutionComponent` keyed by tool-call ID, before `tool_execution_start`; later updates call `updateArgs` on the **same component**. `message_end` marks its arguments complete; `tool_execution_start` marks execution started, creating a fallback component only if needed ([interactive-mode.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/modes/interactive/interactive-mode.ts)). The component tracks distinct `argsComplete`, `executionStarted`, `isPartial`, error, and expansion flags. Specialized `renderCall` / `renderResult` functions receive current state and can reuse prior components; the generic fallback prints the arguments as JSON and text output ([tool-execution.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/modes/interactive/components/tool-execution.ts), [rendering](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/modes/interactive/components/tool-execution.ts)). **Nuance:** pi shows best-effort *parsed fields*, not necessarily every raw partial-JSON byte. Tool-specific renderers may emphasize just a path, command, or query.

**Tool execution → output.** A tool can call `onUpdate(partialResult)`; agent-core emits `tool_execution_update` and later `tool_execution_end` with the final result and error flag ([agent-loop.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/agent/src/agent-loop.ts)). The TUI replaces the same component's result snapshot in place ([interactive-mode.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/modes/interactive/interactive-mode.ts)). Its content can be text or image, with optional structured `details` ([tool-execution.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/modes/interactive/components/tool-execution.ts)).

**Not every tool streams.** Built-in bash collects process data, emits *cumulative snapshots* at a 100 ms throttle, and flushes its dirty tail on finish ([bash.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/bash.ts), [renderer throttle](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/renderers/bash.ts)). Built-in read and grep do **not** call their `_onUpdate` argument: their contents arrive as **final results**, not a stream of file bytes or search hits ([read.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/read.ts), [grep.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/grep.ts)). What feels right for read/search is that the *result is available to render after completion*.

**Screen ≠ transcript ≠ unbounded bytes.** Final assistant and tool-result messages are persisted at `message_end`, not every partial update ([agent-session.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/agent-session.ts)). On session reload, pi rebuilds call components from saved assistant tool calls and pairs saved results by tool-call ID ([interactive-mode.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/modes/interactive/interactive-mode.ts)). On error/abort it marks pending calls failed ([interactive-mode.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/modes/interactive/interactive-mode.ts)). A successful read **hides its body until expanded**; grep previews 15 lines, bash previews the last five visual lines; expansion exposes the *returned* result, not content beyond upstream truncation ([read renderer](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/renderers/read.ts), [grep renderer](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/renderers/grep.ts), [bash renderer](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/renderers/bash.ts)). Built-in tool results commonly cap at 2,000 lines/50 KB; bash advertises a temp-file path to complete truncated output; read advertises a continuation offset ([truncate.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/truncate.ts), [bash.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/bash.ts), [read.js](https://github.com/earendil-works/pi/blob/v0.87.1/packages/coding-agent/src/core/tools/read.ts)). Pi's strength is *a complete generic lifecycle with per-tool specialization*, not unlimited output or universal default expansion.

## 3. Claude Code: the SDK's rich stream, and the native UI caveat

Claude's public Agent SDK defaults to a completed `AssistantMessage` **per content block**. With `includePartialMessages: true` it additionally exposes raw `StreamEvent`s: `content_block_start` for `tool_use` supplies name and ID; `content_block_delta` with `input_json_delta` supplies partial input; `content_block_stop` closes the block. The SDK consumer must accumulate partial data; these raw events are for the main session, **not subagent token-level deltas** ([official Claude streaming documentation](https://platform.claude.com/docs/en/agent-sdk/streaming-output)). This proves an early tool call and partial arguments are available to a harness. It does **not** prove how Claude's closed-source CLI TUI paints each event.

Claude's first-party Desktop documentation says Normal collapses tool calls to summaries; Verbose reveals every tool call, file read, intermediate step and thinking; the CLI has a `--verbose` equivalent ([Desktop view modes](https://code.claude.com/docs/en/desktop#switch-view-modes)). This documents **visibility policy**, not an exact terminal rendering or latency contract. Do not infer from the SDK event stream that native Claude Code displays raw partial arguments, or from Normal mode that the result is absent from its session data. Its SDK has `tool_progress` and final tool results, but those are separate from streamed *input*. bb's bridge asks for `includePartialMessages: true` ([sdk-session.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/plugins/provider-claude-code/src/bridge/sdk-session.ts#L245-L255)).

## 4. Codex: item and command-output streams; less early argument visibility

The Codex app-server stream consumed by bb contains `item/started`, `item/completed`, `item/commandExecution/outputDelta`, `item/fileChange/outputDelta`, and `item/mcpToolCall/progress`; its generated notification union has **no analogous tool-argument-delta event** ([Codex notification schema](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/plugins/provider-codex/src/generated/codex-app-server/schema/ServerNotification.ts#L79)). This is a claim about **that app-server protocol**, not every model API Codex might call.

Codex's open-source TUI creates an active MCP tool-call cell with the invocation's server/tool/arguments at start, then completes the matching cell with duration and result; it has a fallback if the original active cell is gone ([tool_lifecycle.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/chatwidget/tool_lifecycle.rs#L177-L260)). MCP results have compact Display and fuller Transcript render modes; its formatter caps preview lines while retaining renderable text (and substitutes markers for some large media/resource bodies), so *what the TUI shows* is distinct from wire payloads ([mcp.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/history_cell/mcp.rs#L241-L355), [mcp_result.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/history_cell/mcp_result.rs#L1-L130)). Commands have a five-line default preview ([exec-cell renderer](https://github.com/openai/codex/blob/main/codex-rs/tui/src/exec_cell/render.rs#L40-L75)); the core execution process emits bounded `ExecCommandOutputDelta` chunks before final completion ([exec.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/exec.rs)). **Contrast with pi:** Codex can show a named call from `item/started` and stream command output, but its consumed app-server protocol does not expose token-by-token tool-input construction.

## 5. ACP: a client-agnostic *tool state* contract, not one native UI

ACP defines `session/update` with a `tool_call` announcing a session-unique ID, required human title, optional programmatic name/kind, `rawInput`, `rawOutput`, content, locations and status. `tool_call_update` refines the **same call** with only changed fields. Status distinguishes `pending` (input streaming or approval), `in_progress`, `completed`, `failed`. Content can contain text, image/resource, diff, or a client-owned live terminal referenced by ID. The client may choose how to render it ([official ACP tool-call specification](https://agentclientprotocol.com/protocol/tool-calls)). This protocol is the closest direct example of a **provider-neutral extensible envelope**: optional raw payload plus semantic content and lifecycle updates; name is informational, not an authorization mechanism. ACP is not a single native harness: Zed and other clients choose their own presentation, so no universal “ACP native TUI” behavior is implied by the protocol.

## 6. bb: translation, storage, projection and delivery are separate gates

```text
provider native event
  → provider plugin/bridge translates to ThreadDelta
  → shared delta assembler emits bb ThreadEvent
  → server persists events; WebSocket signals "changed"
  → browser invalidates/refetches server-built timeline projection
  → app renders/possibly folds row and output preview
```

**Input under construction.** bb's pi bridge explicitly classifies `toolcall_start`, `toolcall_delta`, and `toolcall_end` as `coverage: "noise"`; it first emits `item.open` at `tool_execution_start` ([pi visibility](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/plugins/provider-pi/src/visibility.ts#L352-L368), [pi translation](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/plugins/provider-pi/src/delta-translation.ts#L773-L852)). Claude's bridge also silences `tool_use` start and `input_json_delta`; it opens a row on the completed assistant tool-use block ([Claude visibility](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/plugins/provider-claude-code/src/visibility.ts#L550-L605), [translation](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/plugins/provider-claude-code/src/delta-translation.ts#L864-L888)). Codex maps its own `item/started` to `item.open`, then its completion and separate command/file output deltas ([Codex translation](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/plugins/provider-codex/src/delta-translation.ts#L1111-L1225)). ACP merges incoming update snapshots internally, but usually exposes interim generic content only as progress; command snapshots have a specialized path ([ACP translation](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/provider-bridge-acp/src/delta-translation.ts#L130-L158), [updates](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/provider-bridge-acp/src/delta-translation.ts#L684-L765)).

**Shared protocol limit.** `ThreadDelta` has `item.open`, `item.close`, `item.progress`, a few text channels, and `item.outputDelta` channels restricted to `command`/`fileChange`. Tool shape has `args` and `result` but **no provisional-input state or generic result-update channel** ([thread-delta.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/provider-bridge-protocol/src/thread-delta.ts#L125-L295)). Each `item.open` emits a *new* `item/started` even if a call is already open, hence reopening to update args is not a safe high-frequency strategy ([delta-assembler.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/provider-bridge-protocol/src/assembler/delta-assembler.ts#L1330-L1381)). `item.progress` carries a one-line message and is throttled by default to 500 ms; command output snapshots are diffed into command-only output deltas ([delta-assembler.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/provider-bridge-protocol/src/assembler/delta-assembler.ts#L1530-L1591), [output](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/provider-bridge-protocol/src/assembler/delta-assembler.ts#L1740-L1818)).

**Result retention versus display.** bb's *specialized* projected `file-read` and `search` row types have no result-content field and their detail renderer returns `null`: content is **not accessible through those specialized rows** ([row types](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/thread-view/src/event-projection-message.ts#L245-L270), [renderer](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/apps/app/src/components/thread/timeline/TimelineRowDetails.tsx#L281-L283)). **Important provider distinction:** bb's pi bridge specializes only `bash`, `edit`, and `write`; pi `read`/`grep` are instead **generic `tool` rows**, whose final `resultText` is placed in a `toolCall` result. The specialized loss concerns providers whose bridges classify a call as `fileRead` or `search`, not pi read/grep by default ([pi classifier](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/plugins/provider-pi/src/delta-translation.ts#L219-L305), [generic close](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/provider-bridge-protocol/src/assembler/delta-assembler.ts#L1004-L1024)). Generic command/tool rows above 4,000 characters are delivered inline as a 2,000-head/1,000-tail preview with a separate availability marker; do not confuse that policy with model-facing truncation ([timeline-output-preview.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/apps/server/src/services/threads/timeline-output-preview.ts#L1-L52)). Completed turns default to a summary plan unless set to `flat`, in which case individual messages are planned ([timeline-row-plan.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/thread-view/src/timeline-row-plan.ts#L25-L96)).

**Delivery and latency.** Server WebSocket messages identify a changed thread, rather than carrying projected tool content ([hub.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/apps/server/src/ws/hub.ts#L805-L825)); client invalidation debounces to 50 ms/200 ms max on fine pointers or 150 ms/400 ms max on coarse pointers, then refetches projection ([realtime-cache-effects.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/apps/app/src/hooks/realtime-cache-effects.ts#L35-L59)). Separately, `VisibleTextBuffer` holds any non-newline text until a newline or close ([visible-text-buffer.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/thread-view/src/visible-text-buffer.ts#L28-L57)). The map's [baseline](https://github.com/IlyaM/bb/issues/4) measured these effects; these numbers are not inferred from pi's TUI architecture.

**Extensibility boundary.** bb's public `experimental_timelineRenderer` allows a provider plugin to customize the **expanded body** of its generic `tool` or plugin-owned extension row. Core row kinds—command, file-read, search, etc.—remain core-rendered; the header remains host-rendered. It is **not** a whole-timeline replacement or a remedy for content lost before projection ([app-contract.ts](https://github.com/IlyaM/bb/blob/7e8ec7e76e097a3591b611d3e9ccc14343da8cd8/packages/plugin-sdk/src/app-contract.ts#L1890-L1925)). bb *does* have declarative per-row presentation metadata and typed provider translation; a generalized lifecycle should preserve those strengths rather than hardcoding pi names in core.

## 7. At-a-glance comparison

| Capability | pi native | Claude Code native / SDK | Codex native / app-server | ACP protocol / clients | bb today |
|---|---|---|---|---|---|
| Earliest named call | Model's `toolcall_start` | SDK `tool_use` block start; CLI paint not verified | `item/started`, usually complete args | `tool_call`, name optional, title required | pi/Claude wait for later execution/completed block; Codex/ACP start earlier |
| Arguments before execution | Mutable parsed object | SDK raw `input_json_delta`; native presentation not verified | No tool-arg delta in consumed app-server notifications | `rawInput` can be updated on same ID | No tool-arg channel or safe item refinement |
| Partial result | Generic `onUpdate` snapshot; tool opt-in | SDK tool progress; native output UI not inferred | Command output deltas; MCP progress | `tool_call_update` content/rawOutput/terminal | Command/file-change output; generic one-line progress |
| Read/search final contents | Returned; read hidden until expanded | Available in SDK result; native display policy varies | Provider item type/renderer-dependent | Can be content blocks or rawOutput | Specialized read/search rows have no body; pi read/grep use generic tool rows with final result |
| Identity and history | Tool-call ID, final assistant+result messages | Tool-use ID; SDK complete blocks/results | Item/call ID, active+completed cells | Session-unique toolCallId | Provider ID mapped to bb item ID; reopen duplicates starts |
| Presentation | Per-tool renderers + generic fallback | Native view modes; internals unverified | Separate command/MCP cells, compact/full views | Client decides | Core row renderers + limited plugin expanded-body slot |

“Native” means an implementation separate from bb, **not** identical behavior across all versions/settings. For ACP, the protocol—not a single client—is the native comparison.

## 8. Design principles suggested by the evidence, *without deciding the ticket*

1. **Represent the phases, not specific tools.** A stable identity and distinct input-under-construction, executing, partial result, and final/error states cover pi, Claude, Codex, ACP, and future providers. Missing partial information is valid: Codex may start with complete args, read may produce only a final result.
2. **Separate generic data from optional semantic interpretation.** Keep room for typed content blocks (including images, resources, diffs and terminal references), raw provider payload, semantic kind/presentation, and plugin-owned renderers without forcing every provider through the `bash` or `read` shape. ACP and pi illustrate two complementary extensibility styles.
3. **Separate transient update transport, durable evidence and UI preview.** A 100 ms cumulative snapshot, a 500 ms progress label, and an immutable final result are different contracts. “Everything available to the client” need not mean every token is a database row or every byte occupies screen height.
4. **Avoid false claims of capability.** If a provider only supplies a final result, show it when it arrives; don't fabricate partial output. If media is represented by a marker or a model-facing result is truncated, say so. Ensure read/search content has an actual representable destination before tweaking expansion UI.
5. **Design for interruption, refinement and recovery.** ACP updates, pi aborts, Codex cell fallback, bb's duplicate-open behavior and browser reconnection expose why provisional identity, completion and replay semantics need to be specified independently of a nice-looking row.

Open decisions for the ticket: best-effort parsed argument snapshot versus raw fragments versus both; whether transient updates use replaceable snapshots or append deltas (and reset/replay semantics); how final generic result blocks are persisted and recovered; what an absent value means; and whether presentation/plugin hooks need changes. None of those follows automatically from “copy pi”: pi's advantages partly come from a single local process, while bb crosses a bridge, daemon, server and browser.
