How bb handles tools across providers

The execution plumbing is substantially shared. The semantics of a tool, its early visibility, its result, and its presentation are not. Four adapters translate different native streams into one delta grammar; that grammar then branches into specialized items whose result capacity varies. Several apparent provider differences are actually the same missing contract expressed four ways.

Scope and method. Static source trace of Pi, Claude Code, Codex and ACP through translation, shared assembler, projection and browser UI. This is not a runtime census or a percentage-of-code measurement. “Shared” means the same code handles all providers once they emit normalized deltas; “provider-specific” means an adapter must understand its native wire. Recommendations are candidate seams, not decisions for the active wayfinding ticket. Source links are pinned to the audited commit; a separately linked earlier research artifact can provide native-TUI context.

Executive findings

Substantial reusable spine

All four emit ThreadDelta item.open/item.close into one assembler, event model, projection, timeline contract and host renderer. The bridge kit also shares formatting, bounding, tool-call RPC and some argument utilities. This is not four independent thread views.

Semantics fragment before the spine

Each adapter maps native tools into command, fileChange, fileRead, search, tool, etc. Shared presentation helpers do not unify classification or preserve a common result envelope.

Specialization currently loses output

fileRead/search shapes contain location/query but no result. Their assembled items and UI rows likewise lack it. Claude explicitly omits their result on close; ACP extracts generic output text but the specialized item cannot retain it.

Streaming is asymmetrical

Pi and Claude suppress partial argument events; ACP merges same-ID updates but renders most non-command updates as throttled text progress; Codex exposes no argument-delta event in this translator. The normalized grammar has no general provisional input/result update.

Where reuse begins and ends

Native SDK / ACP stream→Provider-specific parser, identity & classification→Shared ThreadDelta grammar→Shared assembler + durable events→Shared projection + server timeline→Host row + optional plugin body
  1. Native translation is necessarily specific. Pi uses tool_execution_* and assistant message updates; Claude uses assistant tool_use and subsequent user tool_result; Codex uses item started/completed and output delta notifications; ACP uses tool_call and tool_call_update. Their native parsing, ID correlation, status translation and data extraction must stay adapter-local. Pi · Claude · Codex · ACP.
  2. Normalized lifecycle is common, but narrow. The grammar has item.open, item.close, item.progress, text deltas, and output deltas only for command/fileChange; item.progress.snapshot is limited to background tasks/delegations. It has no general typed input-refinement or tool-result snapshot operation. Delta contract.
  3. Assembler and browser are shared. The assembler converts shapes into ThreadEventItem; thread-view projects event rows; the app selects a host body by workKind. Presentations are small declarative metadata, not executable provider UI. Opened items · Rows · Bodies.
  4. Presentation vocabulary is partly shared already. The bridge kit provides common read/search/web/tool labels, icons and bounded titles; provider-specific modules still supply classification, richer metadata and exceptions. Reuse of a label builder is not reuse of a lossless semantic model. Shared presentation helpers · Claude classification · ACP classification.

“No translated delta” does not imply the upstream provider has no such capability. In particular, this source audit only establishes what bb accepts and emits today.

Three concrete paths where one tool becomes less observable

1. Classifying a read or search can erase its result

The normalized fileRead shape is path/cmd; search is mode/query/path/cmd. The shared assembler's buildFileReadItem and buildSearchItem copy only those fields and status. On close, it rebuilds those items without any resultText. The thread-view row likewise contains only those descriptors, and the app body returns null. Thus “read result missing” is not merely an unimplemented React component: it is absent through the model chain. Pi read/grep happen to remain generic and retain text, demonstrating that provider classification, not inherent tool semantics, determines observability. Shape · Assembler · Close · UI.

2. Progress and preliminary results have a command-shaped channel

item.outputDelta accepts only command/fileChange channels, and command.outputSnapshot is special-cased. Non-command item.progress takes an optional text message, not a full snapshot; assembler emits item/toolCall/progress and throttles it. ACP can merge rawInput/rawOutput, but only a command gets a durable-ish UI output snapshot; Pi's non-command partial results degrade to a text summary. This is a contract hole shared across adapters, not a reason to duplicate each provider's snapshot logic. Grammar · Assembler.

3. Generic rows have a constrained customization and full-output route

The plugin slot resolves one tool body renderer by the provider plugin ID; it does not dispatch by tool name, nor allow an independently installed tool plugin to own one call. It also excludes command/read/search and keeps the header host-owned. Its props contain {arguments, output} from the timeline row; server pages preview tool/command outputs past 4,000 characters, and full output loads separately for those core bodies. A custom renderer must use Original for the host's own retrieval route; the plugin payload alone is not a promise of complete output. Resolution · Props · Preview · Recovery.

Suggested order of investigation, not a build plan

  1. Prove one lossless call envelope end to end. Representative read, search, command, generic extension and MCP results should survive classified → assembled → persisted → projected → SDK/CLI → browser; errors and large results included. This is the highest-leverage structural gap.
  2. Prove provisional lifecycle on two unlike feeds. Pi/Claude partial argument announcements versus ACP same-ID updates; retain stable identity, recoverable current state and one terminal outcome. This follows the already-settled protocol and push-recovery decisions, rather than inventing a provider-specific workaround.
  3. Then choose customization ownership. First demonstrate the host fallback and provider-owned enrichment. Only add tool-name registration for independent integrations with a concrete collision/trust model; do not let the current provider-wide tool renderer silently become that API.
  4. Audit omissions separately. Suppressed/duplicate protocol signals and model gaps are different: preserve distinct activities while deduplicating true repeated lifecycle records by identity. Existing presentation.suppress and inferred bundles are relevant to the larger map but are not a substitute for carrying tool results.
Limits and open checks. This is source evidence, not measured prevalence. No production provider-corpus counts, interactive browser trace, or confirmation that Codex's upstream MCP API exposes result blocks omitted by bb's schema were performed here. The current report does not settle whether third-party tool integrations should register browser renderers, only identifies where that decision bites. It does not alter or resolve the claimed wayfinding ticket.
